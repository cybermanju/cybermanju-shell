# CyberManju OS — Asterinas ABI baseline

**Asterinas remains the primary kernel/base.** The app, intended GPUI shell and candidate compositor do not yet form a verified native Asterinas desktop. This inventory advances `OS-A0`; it does not complete A0 or authorize implementation. Existing app/security tasks and personalization controls remain unchanged.

## What blocks the desktop first

1. **A native GPU stack is not established.** The local PCI/MSI-X/DMA work is real, but does not implement GPU submission, NVIDIA RM/GSP, an AMD driver or an accelerated Vulkan ICD. No physical GPU is available here.
2. **The compositor needs more than a framebuffer.** Asterinas has basic DRM/GEM/KMS source, but the inspected simpledrm path is CPU scanout. DMA-BUF, fences, usable GPU render nodes, the compositor's required modesetting path and evdev/seat/session integration need resolution.
3. **The existing app needs its actual Linux userspace runtime.** Tauri/Wry depends on GTK3/WebKitGTK 4.1 and their process, IPC, graphics and native-library closure. A Linux ABI goal or a freestanding VM init does not demonstrate that closure works.
4. **GPUI presentation feedback is still missing.** The newer Linux nested tests pass on CPU software Vulkan, but request zero per-buffer presentation feedback objects. Physical presentation FPS remains `null`; the physical-GPU gate correctly rejects the run.

The [active architecture plan](CYBERMANJU-OS-PLAN.md#active-plan--asterinas-first-2026-10-20) retains dependency gates A0–A8. Ubuntu+niri is a comparison environment only, not an automatic replacement for Asterinas.

## How to read the evidence

- **Source-present:** an implementation or dependency exists in inspected source; runtime compatibility is not established.
- **Tested in VM:** retained logs demonstrate the stated behavior in Asterinas under CPU/QEMU, for that snapshot and configuration only.
- **Software-only:** retained Linux-host/nested tests use CPU rendering; this is not execution on Asterinas or physical scanout.
- **Unresolved:** the needed target configuration, interface or end-to-end experiment has not been demonstrated.
- **Unsupported:** the inspected path explicitly rejects the operation or lacks the required implementation. This is not a statement about every future Asterinas revision.

## Upstream facts versus local test results

### Upstream Asterinas

The [upstream README](https://github.com/asterinas/asterinas#introducing-asterinas) describes a Linux-compatible kernel with 240+ syscalls and an experimental NixOS distribution. This is a project direction and broad coverage statement, not certification of any particular libc, syscall variant, ioctl or desktop application.

The [0.19 graphics announcement](https://asterinas.github.io/2026/10/13/announcing-asterinas-0.19.0.html) documents `/dev/dri`, GEM dumb buffers, KMS and Xorg's modesetting driver with **Mesa software OpenGL**. It does not demonstrate accelerated Vulkan, Wayland, GPUI or Tauri in this fork. The [distribution guide](https://asterinas.github.io/book/distro/index.html) explicitly says Asterinas NixOS is not production-ready and not all NixOS configuration combinations are supported. Upstream NixOS availability is a candidate rootfs strategy, not an accepted product image.

### Local Asterinas checkpoint — tested in VM

The **15-patch MSI-X checkpoint** has retained results for **20 NVport, 4 platform, 13 PCI, 13 PCI+VT-d and 256 reported OSTD tests**, with three VMX/VMCS/EPT bodies explicitly skipped. Read `EVID/nvidia-msix-transaction/test-counts.json:1–66` and `README.md:7–20`; do not interpret the reported total as VMX coverage.

NVMe, modern Virtio and legacy Virtio completed 4096-byte reads, writes, fsync and readback, with the post-poweroff raw disks checked. Three full-kernel CPU/QEMU boots passed: normal, VT-d and multifunction NVMe+VT-d. Sources: `EVID/nvidia-msix-transaction/consumer-io/run-final/result.json`, `cpu-boot-final/result-*.json`, and `/workspace/asterinas-gpui/local-prs/PR_NOTES.md:494–512`. The JSON records GPU/RM/GSP/firmware flags as false. These are emulated-device correctness results, not physical-drive power-loss guarantees or GPU performance.

A **later 16th device-worker patch** is present in the current tree. Its separate notes report a different platform-test count and callback-drain scope (`EVID/nvidia-device-worker/continuation-notes.md:2–20`). Do not attach the 15-patch 256-test matrix to this newer tree or claim callback completion proves DMA/IRQ/GSP quiescence. Exact future test inputs must use the corresponding saved source/patch manifests.

## Preserve the existing personalization contract

This is compatibility work, **not a second settings application**. The [active plan's inventory](CYBERMANJU-OS-PLAN.md#personalization-is-a-compatibility-requirement-not-a-new-settings-app) remains the detailed contract, including values/defaults and storage semantics.

`APP/src/composables/useTheme.ts:21–29,46–92,130–131` already loads/migrates and writes `cybermanju_theme_v1` and `cybermanju_shell_style`. Keep current themes/accents/density/glass/motion/system-following behavior and panel docking. `APP/src/utils/customWallpaper.ts:19–30,80–104,116–177` preserves URL/file records in per-install IndexedDB with the 20 MiB cap; WebView storage origins and file permissions must survive any target packaging change. Wallpapers are not a server-upload feature.

Retain keyboard/KPL, touch/JSON, locale `cybermanju.locale.v1`, existing Settings navigation and accessibility. Treat app keyboard handlers and gestures separately from compositor-global bindings, evdev and touch-device support. Browser-local persistence does not automatically become shared GPUI settings; define a versioned, permission-scoped adapter and app-versus-desktop ownership without a competing store. Pinia-only view/sidebar/refresh durability remains unverified. No adapter or profile export has been implemented by this inventory; credentials and server/broker configuration must remain outside cosmetic exports.

## Next experiments, in blocking order

These are **proposals only**, not commands executed or newly authorized. Suggested owners are roles to assign, not people already committed to the work.

1. **A0 — release/integration owner:** freeze source/patch manifests and hashes for the app, Asterinas and GPUI review; archive `target/presentation-review`; pin compiler, libc/loader, rootfs/init/services, Niri/Smithay, firmware policy and named VM/physical targets. 2. **A1 — userspace/runtime owner:** boot the selected rootfs repeatedly in disposable QEMU and run small exact-target Rust/libc probes for loader/TLS, threads/futex/epoll, FD-bearing Unix IPC, filesystem sync/reopen/locks, `/proc`, entropy/time, DNS/TLS and process shutdown. 4. **A3 — independent AMD/NVIDIA driver owners:** resolve vendor UAPI, memory, submission, DMA isolation, interrupts/workers, reset and approved firmware; NVIDIA additionally needs genuine RM/GSP lifecycle.
